## 1. Authorship

### 1.1 Author data model

All articles get one author for now: **Grant Tilus**. Build this as a real data model, not a hardcoded string, so it survives a second author later.

Add an `authors` collection to `src/lib/marketing-content.ts` (or a new `src/lib/authors.ts` imported there):

```ts
export type Author = {
  slug: string;            // "grant-tilus" — used in the /authors/[slug] URL
  name: string;            // "Grant Tilus"
  jobTitle: string;        // e.g. "Founder, Accountability Guild"
  bio: string;             // 2-4 sentences, third person, for the author page and article byline
  avatarUrl: string;       // square headshot, min 400x400
  sameAs: string[];        // LinkedIn, X/Twitter, personal site — whatever is real and current
};

export const authors: Author[] = [
  {
    slug: "grant-tilus",
    name: "Grant Tilus",
    jobTitle: "Founder, Accountability Guild",
    bio: "…",
    avatarUrl: "/authors/grant-tilus.jpg",
    sameAs: [],
  },
];
```

Then add an `authorSlug: "grant-tilus"` field to every entry in the existing article inventory (all 13 current articles) instead of leaving authorship implicit. This is what makes author pages "dynamically populated" per the request — the author page is generated by filtering articles on `authorSlug`, not hand-maintained.

**Open item for Grant:** the bio, job title, headshot, and any real social links (`sameAs`) need real content before this ships — placeholder bios read as thin/AI-generated and undercut the E-E-A-T signal this section exists to build.

### 1.2 Author pages (`/authors/[slug]`)

Each author page should include:

## 2. Article and author structured data (JSON-LD)

Source: [Google's Article structured data guide](https://developers.google.com/search/docs/appearance/structured-data/article), fetched 2026-07-16. Google has **no strictly required** Article properties — it's a "add what applies" model — but author markup has explicit best practices Google calls out separately, and the current site is missing them entirely.

### 2.1 What to add to existing Article JSON-LD

The current `/resources/[slug]` schema already has `headline`, `description`, `datePublished`, `dateModified`. Add:

```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "Goal Setting That Actually Sticks: A Practical Step-by-Step Guide",
  "description": "…",
  "image": [
    "https://accountabilityguild.com/resources/goal-setting/hero-1x1.jpg",
    "https://accountabilityguild.com/resources/goal-setting/hero-4x3.jpg",
    "https://accountabilityguild.com/resources/goal-setting/hero-16x9.jpg"
  ],
  "datePublished": "2026-04-10T08:00:00-05:00",
  "dateModified": "2026-04-10T08:00:00-05:00",
  "author": [
    {
      "@type": "Person",
      "name": "Grant Tilus",
      "url": "https://accountabilityguild.com/authors/grant-tilus"
    }
  ],
  "publisher": {
    "@type": "Organization",
    "name": "Accountability Guild",
    "url": "https://accountabilityguild.com"
  }
}
```

Notes, straight from Google's guidance:
- `author` must be an **array**, even with one author, so a second author can be added later without changing the shape (`"author": [{...}]`, not `"author": {...}`).
- `author.name` should contain **only the name** — no job title, no honorific, no "by" prefix. Job title goes in `jobTitle` if you want it in schema at all; it's optional and not required for the rich result.
- `author.url` should point to the author page from Section 1 (an internal profile page), which is exactly what Google recommends: *"If the URL is an internal profile page, we recommend marking up that author using profile page structured data. You can use the `sameAs` property as an alternative."*
- Use `@type: "Person"` — not `"Organization"` and not `"Thing"`.
- `image` should be a **real image array**, not omitted (see Section 3 — this is currently empty because the site has zero images anywhere). Google recommends multiple aspect ratios: 16x9, 4x3, 1x1, each at least 50,000 total pixels (e.g., 696×392 or larger for 16x9).
- Use `BlogPosting` (not bare `Article`) — most accurate schema.org subtype for this content; `NewsArticle` doesn't fit.
- Only set `dateModified` to a value different from `datePublished` when the article is actually revised. The current audit found all 13 articles have identical `datePublished`/`dateModified` values from the original batch — that's fine as long as it stays true; don't bump `dateModified` on unrelated deploys.

### 2.2 Author page schema

Mark up each `/authors/[slug]` page as `ProfilePage` with a `Person` as the `mainEntity`, per Google's [Profile page structured data guide](https://developers.google.com/search/docs/appearance/structured-data/profile-page):

```json
{
  "@context": "https://schema.org",
  "@type": "ProfilePage",
  "mainEntity": {
    "@type": "Person",
    "name": "Grant Tilus",
    "jobTitle": "Founder, Accountability Guild",
    "description": "…same short bio as the page…",
    "image": "https://accountabilityguild.com/authors/grant-tilus.jpg",
    "url": "https://accountabilityguild.com/authors/grant-tilus",
    "sameAs": []
  }
}
```

Skip the social interaction-counter fields (`interactionStatistic`, `agentInteractionStatistic`) shown in Google's example — those are for forum/social-profile use cases, not relevant here. Populate `sameAs` only with real, live profile URLs (LinkedIn, X, personal site) — an empty array is fine until those exist; don't fabricate links to satisfy the schema.

### 2.3 Validation

Before shipping, run every changed page (one article, the author page) through the [Rich Results Test](https://search.google.com/test/rich-results) and fix any critical errors. Non-critical warnings are worth reviewing but not blocking. After deploy, spot-check with the URL Inspection tool in Search Console (the repo already has GSC configured per `docs/marketing/seo-founding-articles-baseline-2026-04-12.md`) and resubmit the sitemap once the new author URL is live.

## 3. Content imagery

Current state per the 2026-07-13 audit: **zero `<img>` tags anywhere on the site** — no hero images, no diagrams, no screenshots. This is the single biggest content-depth gap versus competitors and it's also why Article schema's `image` field has been empty.

### 3.1 Hero image

- **Data model:** add a `heroImage` field to each article entry (or convention-based: `/public/resources/[slug]/hero.jpg` + a generated set of crops). Every article needs one before it ships — this isn't optional per-article, it's a required field going forward.
- **Aspect ratios:** generate (or source) each hero at 16:9, 4:3, and 1:1, matching Google's recommendation for the Article `image` array (Section 2.1). If only one master image exists, crop programmatically at build time rather than hand-producing three files per article.
- **Placement:** render the hero at the top of the article template, above the H1 or immediately below it (pick one and apply consistently across all 13+ articles) — this is also the image most likely to be used as the `og:image`/Twitter Card image, so it should already exist in the metadata pipeline (`src/lib/seo.ts`) as a reusable value, not duplicated between the schema and the `<head>` tags.
- **Alt text:** required, descriptive, not keyword-stuffed — describe what's actually in the image, not the article topic restated.
- **Delivery:** use Next.js `<Image>` (`next/image`) for automatic responsive sizing, lazy loading below the fold, and format negotiation (WebP/AVIF) — don't hand-roll `<img>` tags. Set `priority` on the hero image specifically, since it's above the fold and shouldn't lazy-load.
- **Source:** decide now whether hero images are stock/licensed, custom illustration, or AI-generated, and apply one approach consistently — a mismatched mix (some stock, some AI, some hand-drawn) will look inconsistent across the resource library faster than no images at all.

### 3.2 In-line content images

Not every paragraph needs an image, but long-form articles with zero visual breaks (which is the current state of all 13 articles) hurt both readability and the "out-teach incumbents" goal flagged in the SEO audit. Rules for where in-line images earn their place:

- **Concept/process diagrams** — anywhere the article describes a sequence, framework, or structure in prose that would be clearer as a simple diagram (e.g., the four-act cycle, a decision tree, a before/after comparison). This is the highest-value use given the product's own operating model is already diagram-shaped.
- **Comparison tables** — not strictly an "image," but treat as equivalent-value visual breaks; use real `<table>` markup, not a screenshot of a table.
- **Screenshots** — only if/when there's a real product UI worth showing; don't fabricate UI mockups that don't match the actual app, since `docs/product/capability-ui-inventory.md` already exists specifically to prevent overclaiming capabilities.
- **Frequency guideline:** roughly one visual element per 300-500 words of body content on long-form articles, concentrated at natural section breaks (after an H2), not evenly spaced for its own sake.
- **Technical requirements for every in-line image:** descriptive `alt` text, explicit `width`/`height` (or fill container) to avoid layout shift, lazy-loaded via `next/image` (everything below the fold), and a visible caption where the image isn't self-explanatory from surrounding text.
- **File weight:** compress and serve via `next/image`; don't let a well-intentioned diagram push page weight enough to hurt Core Web Vitals — the audit already flagged Core Web Vitals as an unverified open item, so new images shouldn't be what finally triggers a real problem there.

## 4. SEO rules: H1, Quick Summary, Title Tag, Meta Description

Google's official guidance ([title links](https://developers.google.com/search/docs/appearance/title-link), [snippets/meta descriptions](https://developers.google.com/search/docs/appearance/snippet), fetched 2026-07-16) doesn't publish hard character limits for any of these — display is truncated to fit device width, not a fixed count — but the practical targets below keep titles and descriptions from truncating on typical desktop/mobile search results, which is the de facto standard most SEO tooling (including Ahrefs/Semrush, both already connected to this workspace) checks against.

### 4.1 H1

- Exactly **one `<h1>` per page** — the current site already does this correctly per the audit; keep it true as author pages and any new templates are added.
- The H1 must be the single most visually prominent text on the page. Google explicitly warns that if it detects multiple large, prominent headings with equal visual weight, it may pick the wrong one for the title link — so no competing large text (subheads, hero taglines) should visually outweigh the H1.
- The H1 does not have to be character-for-character identical to the `<title>` tag, but it should express the same primary topic — Google pulls from both and prefers alignment; a mismatch invites Google to substitute its own title link text instead of using what's authored.
- For articles: H1 = the article's actual headline (matches `headline` in the Article schema). For the author page: H1 = the author's name. For `/resources`: H1 = something like "Field Notes" or the actual hub name, not a generic "Resources."

### 4.2 Quick Summary (on-page TL;DR block)

This refers to the short summary block that should sit at the top of every long-form article, above the first H2 — separate from the meta description (which lives in `<head>` and is never seen by the reader on the page itself).

- **Purpose:** answer "what will I learn / is this worth reading" in the first 2-3 sentences a reader (or an AI answer engine, or a featured-snippet crawler) sees. This is also the single best fix for the article's `read time` mismatch problem flagged in the 2026-07-13 audit — a tight Quick Summary makes thin content obvious immediately rather than after a misleading "14 min read" label.
- **Length:** 2-4 sentences, roughly 40-80 words. Long enough to be genuinely useful, short enough to stay skimmable.
- **Content:** state the concrete takeaway or outcome, not a meta-description-style teaser. It should be able to stand alone as a correct, complete answer to the implied query — this is what makes it eligible for Google's featured snippet / AI Overview extraction, per Google's own snippet guidance that snippets are "designed to emphasize and preview the page content that best relates to a user's specific search."
- **Must not duplicate the meta description verbatim** — they serve different readers (search results page vs. the article itself) and reusing the same string in both places wastes an opportunity to reinforce the same information two different ways.
- **Placement:** immediately after the H1 and hero image, before the first H2. Visually distinct (e.g., a bordered callout or bold intro paragraph) so it reads as intentional, not just the first sentence of the article.
- Apply retroactively to all 13 existing articles, not just new ones going forward — this is a cheap, high-value fix per-article.

### 4.3 Title tags (`<title>`)

Rules, direct from Google's title-link guidance:

- Every page must have a unique, non-empty `<title>` element — no defaults, no shared boilerplate.
- **Descriptive and concise.** Avoid vague titles ("Resources," "Author") and avoid unnecessarily long/verbose ones — Google truncates to fit the display, so anything padded past what's needed gets cut with no control over where.
- **No keyword stuffing** — don't repeat the same term/phrase multiple times in one title.
- **No repeated/boilerplate text across pages** — every resource article's title must be genuinely distinct, not a shared template with one word swapped.
- **Brand suffix, once, consistently:** append `— Accountability Guild` (or similar delimiter) to page titles rather than putting brand language in every title. Practical target: keep the full string (title + brand suffix) around **50-60 characters** so it doesn't truncate on a typical desktop SERP — this is a practical convention, not a Google-stated hard limit.
- **Match language/writing system of the page content** — not a live concern today since the site is English-only, but keep in mind if translated content is ever added.
- Author pages: `[Author Name] — Accountability Guild`. Resource articles: keep the existing pattern already confirmed working by the audit (unique, well-formed, no duplication) — just verify author pages follow the same convention.

### 4.4 Meta descriptions

Rules, direct from Google's snippet guidance:

- **Unique per page** — no shared/duplicated descriptions across articles (already true today per the audit; keep it true for author pages too).
- **Write a real summary, not a keyword list.** Google explicitly calls out keyword-string meta descriptions as the "bad" example pattern to avoid.
- **Include concrete, specific information** where relevant — for articles, that might mean naming the actual method or framework covered rather than a generic teaser; for the author page, it might mean the author's role and what the reader will find in their articles.
- **Summarize the whole page**, not just the opening paragraph — Google's own "bad" example is a description that only reflects the article's first few sentences rather than its overall content.
- Practical target: **~150-160 characters**, enough to fully render on both desktop and mobile SERPs without truncation — again a practical convention (Google states no fixed limit, only that display truncates to fit device width).
- Meta descriptions are a **suggestion** to Google, not a guarantee — Google may still generate its own snippet from on-page content if it judges that more relevant to a specific query. Writing a good one increases the odds Google uses it, but isn't a hard override.
